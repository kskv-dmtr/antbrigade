# ant brigade

Статический сайт на Astro поверх базы в Notion. Notion остаётся единственным
местом редактирования; сайт только показывает данные.

Боевой адрес — [www.antbrigade.fun](https://www.antbrigade.fun).

**Здесь — что делать: выгрузить, запустить, проверить, выложить.** Как сайт
устроен и почему именно так — в `docs/`, начиная с `docs/ant brigade.md`.
Там же перечислены решения, которые выглядят как недосмотр, но сделаны
намеренно (`docs/Решения.md`), и открытые дыры (`docs/Что не сделано.md`).

```
antbrigade/
├── data/
│   ├── albums.json       выгрузка из Notion
│   └── links.json        ссылки на площадки со страниц album.link
├── docs/                 документация по устройству сайта
├── .github/workflows/
│   └── sync-notion.yml   ежечасная синхронизация с Notion
├── scripts/
│   ├── fetch-notion.mjs        выгрузка из Notion
│   ├── fetch-covers.mjs        скачивание обложек
│   ├── fetch-thumbs.mjs        скачивание кадров роликов с YouTube
│   ├── fetch-links.mjs         сбор ссылок на площадки
│   ├── doctor.mjs              проверка базы
│   ├── make-icons.mjs          нарезка иконок приложения
│   ├── make-sitemap.mjs        карта сайта после сборки
│   ├── make-static-config.mjs  vercel.json для статической загрузки
│   └── make-zip.ps1            упаковка dist для Vercel Drop
├── public/
│   ├── covers/           обложки, webp, по две ширины на релиз
│   ├── videos/           кадры роликов, webp
│   ├── icons/            иконки приложения
│   ├── manifest.webmanifest
│   ├── robots.txt
│   └── _headers          заголовки для Cloudflare Pages
├── src/
│   ├── lib/              db.js и вычисление имён файлов картинок
│   ├── layouts/Base.astro
│   ├── components/       13 штук, перечислены в docs/Компоненты.md
│   ├── styles/global.css всё оформление, токены в :root
│   └── pages/
│       ├── index.astro           главная: Latest Releases и Lucky Finds
│       ├── music.astro           весь каталог с фильтрами
│       ├── videos.astro          все клипы одним списком
│       ├── 404.astro             страница промаха
│       ├── albums/[slug].astro   страница релиза

│       ├── artists/              список и страница исполнителя

│       └── genres/               список и страница жанра
├── astro.config.mjs
└── package.json
```

Собирается **3086 страниц примерно за 17 секунд**. В базе 1100 релизов, 988
исполнителей, 617 лейблов, 76 клипов и 298 жанров.

## Обновить данные из Notion

```bash
npm run sync
```

Занимает около минуты. Токен не нужен — страница опубликована, читаем её
публичный API. Скрипт забирает все записи, разбивая выборку по диапазонам дат
(Notion отдаёт максимум ~999 записей за запрос), и перезаписывает
`data/albums.json`.

Две особенности, важные для автоматики:

- **Выгрузка детерминирована.** Все сортировки строгие, последним ключом идёт
  `id`, локаль сравнения задана явно. Одинаковые данные всегда дают
  побайтово одинаковый файл — независимо от машины.
- **Если данных не изменилось, файл не перезаписывается.** Меняться в нём было
  бы только время выгрузки, и CI видел бы правку там, где правки нет.

У скрипта нет зависимостей — он работает на голом Node, до `npm ci`.

## Картинки

```bash
npm run covers    # обложки из Notion
npm run thumbs    # кадры роликов с YouTube
```

Оба кладут webp в `public/`, кэшируются по устойчивому имени файла и качают
только недостающее. У каждого есть `--check` (только сказать, есть ли работа)
и `--limit N`.

**Кадры роликов с машины владельца не скачиваются:** прямой доступ к
`i.ytimg.com` закрыт, а Node не ходит через локальный прокси. Из GitHub
Actions они скачиваются сами — ради этого сбор и вынесен в часовой workflow.

## Ссылки на площадки

```bash
npm run links
```

Собирает со страниц `album.link` прямые ссылки на площадки и кладёт в
`data/links.json`. Кэшируется по идентификатору релиза: повторно ходим только
за новыми. За прогон берётся не больше 250 релизов и не дольше 12 минут,
остальное доберут следующие.

На странице релиза показываются **Spotify, Bandcamp и Яндекс Музыка** — то,
чем реально пользуются. Остальное (Tidal, Deezer, Amazon, Pandora, Boomplay,
Anghami, Napster) складывается в файл, но не выводится: забирать их всё равно
бесплатно, а решение о показе меняется одной строкой в `src/lib/db.js`.

Двух площадок нет и не будет — проверено, а не предположено:

- **Apple Music и YouTube.** Odesli не отдаёт их для этого каталога вообще.
  Сверено тремя способами: данные внутри страницы, официальный API
  `api.song.link`, он же с `userCountry=RU` — везде пусто.
- **Звук.** Odesli такой площадки не знает. У самого `zvuk.com` есть приватный
  GraphQL с анонимным токеном, и он работает, но не годится: на выборке из 24
  релизов точных совпадений оказалось 5, а в 18 случаях поиск уверенно
  возвращал чужой альбом. Плюс Звук отвечает `418` на запросы из Node и
  блокирует адреса дата-центров — то есть в CI это не заработало бы.

**Важно про сбор.** `album.link` при потоке запросов отдаёт страницу без
ссылок, не сообщая об этом: код `200`, разметка на месте, площадки пустые.
Поэтому пауза 2.5 секунды, придержанный ответ не считается результатом и
повторяется в следующий прогон, а пять подряд включают паузу на полторы
минуты. Как это отличается от честного «площадок нет» — в
`docs/Синхронизация.md`.

## Проверка базы

```bash
npm run doctor
```

Читает выгрузку и печатает, что в базе не заполнено и что рассыпалось.
Ничего не чинит и никуда не ходит: правки делаются в Notion, скрипт лишь
говорит, какие страницы открыть.

Пропуски и поломки разделены намеренно. Пропуск — незаполненное поле:
релиз без лейбла, исполнитель без страны. Это вопрос к содержимому, и
часть таких пропусков нормальна — у сборников не бывает исполнителя, у
`Self-released` нет страны.

Поломка помечена `!!` и означает расхождение внутри самих данных:

- **висящая связь** — след страницы, ушедшей в корзину Notion. Из вида базы
  она пропала, а идентификатор в поле релиза остался. На сайте не видна,
  неразрешимые связи там отбрасываются, но в базе это мусор. В отчёте
  печатается прямой адрес — открыть в Notion и снять лишнюю метку;
- **ненайденный файл** — обложка или кадр, которых нет в `public/`;
- **повтор имени или адреса** — два исполнителя с одинаковым именем разъедутся
  по двум страницам, два релиза с одинаковым slug затрут друг друга;
- **год против даты** — в базе разошлись два поля об одном и том же.

С ключом `--strict` скрипт выходит с ненулевым кодом, если нашлись поломки:

```bash
npm run doctor -- --strict
```

Это на случай, если проверку захочется поставить в workflow. Сейчас она там
не стоит: висящие связи — не повод останавливать сборку сайта.

## Автоматическое обновление

Настроено через GitHub Actions: `.github/workflows/sync-notion.yml`.

```
раз в час
   ↓ выгрузка из Notion
что-то изменилось, не хватает обложек, кадров или ссылок?
   ↓ да
npm ci → добрать обложки, кадры и ссылки
   ↓
npm run build              (проверяем, что сайт вообще собирается)
   ↓ собрался
коммит данных и картинок → push
   ↓
Vercel видит пуш и пересобирает сайт
```

От записи в Notion до появления на сайте — до часа плюс пара минут на сборку.
Прогоны без изменений укладываются в полминуты и обрываются на второй строке.

**Бот правит те же файлы, что и человек.** Перед своим пушем нужно подтягивать
чужие коммиты; конфликт в `data/albums.json` разрешается не выбором версии, а
свежей выгрузкой — она даёт и правки бота, и то, ради чего правился скрипт.

### Что нужно сделать один раз

1. Создать репозиторий на GitHub с именем `antbrigade`. Корнем репозитория
   должно быть содержимое папки `antbrigade`: `package.json` обязан лежать в
   корне. Приватный тоже подойдёт.
2. Залить файлы. `.gitignore` уже настроен — `node_modules`, `dist` и
   `dist.zip` в репозиторий не попадут.
3. Связать с Vercel: в проекте на Vercel **Settings → Git → Connect**. Если
   проект создавался через Drop, он не привязан к репозиторию — привязать
   можно здесь же, заново создавать не нужно.
4. Проверить: на вкладке **Actions** запустить задачу вручную кнопкой
   **Run workflow**. Так видно результат сразу, а не через час.

### Необязательно: секрет VERCEL_DEPLOY_HOOK

Vercel обычно реагирует на пуш сам. Если по какой-то причине не среагирует на
коммит от бота, можно завести Deploy Hook (Vercel: Settings → Git → Deploy
Hooks) и положить его адрес в секреты репозитория под именем
`VERCEL_DEPLOY_HOOK`. Тогда workflow дёрнет его напрямую. Без секрета шаг
просто пропускается.

### Настройки, которые может понадобиться поменять

- **Частота.** Строка `cron: '17 * * * *'` — раз в час. Время в UTC, GitHub
  нередко запускает с задержкой в несколько минут. Реже — например
  `'17 */3 * * *'` раз в три часа.
- **Лимит минут.** Для приватных репозиториев бесплатно даётся 2000 минут
  Actions в месяц. Ежечасные прогоны без изменений съедают примерно четверть
  этого. У публичных репозиториев лимита нет.
- **Спячка.** GitHub отключает расписание, если в репозитории 60 дней не было
  активности. Коммиты самой синхронизации активностью считаются, так что это
  грозит только совсем пустым периодам.

## Установка на домашний экран (PWA)

Сайт устанавливается как приложение: своя иконка, запуск без адресной строки.
Service worker для этого не нужен — Chrome убрал его из требований, — поэтому
офлайна пока нет, только установка.

Пересобрать иконки из другого исходника (нужен квадратный PNG, лучше
1024×1024):

```bash
node scripts/make-icons.mjs путь/к/иконке.png
```

Скрипт заодно печатает цвет фона — его нужно вручную вписать в `theme_color`
и `background_color` манифеста, если исходник поменялся.

**При замене иконок менять метку версии в адресах** — она стоит и в
`Base.astro`, и в манифесте. Имена файлов постоянные, и без новой метки у тех,
кто заходил раньше, останется старая картинка: годовой `immutable` однажды уже
оставил на телефонах июльскую иконку после августовской замены.

Две вещи, которые стоит знать:

- **Приложение привязано к домену.** Установленное с `*.vercel.app` и
  установленное с боевого домена — два разных приложения. Ставить имеет смысл
  после привязки домена, иначе придётся переустанавливать.
- **На iOS нет кнопки установки** — только «Поделиться → На экран „Домой“».

## Выложить на Vercel

Хостинг — Vercel, а не Cloudflare Pages, по одной причине: домен `*.pages.dev`
недоступен из России, а `*.vercel.app` открывается.

Проект называется **`antbrigade`**, служебный адрес —
`https://antbrigade.vercel.app`. Боевой домен — **`https://www.antbrigade.fun`**,
он и стоит в `site` в `astro.config.mjs`: отсюда берутся канонические ссылки, и
адрес должен совпадать с тем, по которому сайт реально открывается. Меняете
домен — меняйте `site` и пересобирайте.

Именно с `www`: голый `antbrigade.fun` отдаёт 308 на www-версию. Если в
настройках Vercel основным сделают голый домен, приставку из `site` надо
убрать.

**В `vercel.json` команда сборки обязана идти через npm.** Скрипты карты сайта
и статического конфига висят на хуке `postbuild`, а хуки срабатывают только у
`npm run build`; при `buildCommand: "astro build"` Vercel собирает мимо них, и
карта на боевом сайте не появляется — проверено на 404.

### Обновление сайта

Обычно ничего делать не нужно: правки данных выкладывает бот, правки кода —
пуш в `main`, Vercel пересобирает сам.

Руками, если понадобится:

```bash
npm run deploy
```

### Первая выкладка через терминал

```bash
npm run deploy
```

1. Откроется браузер со входом в Vercel. Аккаунт бесплатный; удобнее всего
   войти через GitHub, но можно и по почте.
2. `Set up and deploy?` — ответить `y`.
3. Область (scope) — свой личный аккаунт.
4. `Link to existing project?` — `n`, проект создаётся впервые.
5. `What's your project's name?` — `antbrigade`.
6. `In which directory is your code located?` — оставить `./`.
7. Настройки сборки определятся сами из `vercel.json`. Подтвердить.

Сборка идёт на стороне Vercel, поэтому локальная папка `dist` в загрузку не
попадает — это указано в `.vercelignore`.

### Способ без терминала: Vercel Drop

Подходит для первой публикации.

```bash
npm run build
```

```bash
npm run zip
```

Дальше открыть [vercel.com/drop](https://vercel.com/drop), войти, перетащить
`dist.zip`, вписать имя проекта `antbrigade`, нажать **Deploy**.

Перетаскивать нужно именно архив, а не папку: в ней 5461 файл, и браузер будет
грузить их заметно дольше. Сборка при этом не запускается — Vercel раздаёт
готовые файлы как есть, а за заголовки отвечает `dist/vercel.json`, который
кладётся туда автоматически после `npm run build`.

**Существенное ограничение:** каждый drop создаёт **новый** проект, обновить
существующий им нельзя.

### Ограничения бесплатного тарифа

Тариф Hobby: 100 ГБ трафика в месяц, чего для этого сайта многократно хватает.
Существенная оговорка — Hobby разрешает только **некоммерческое**
использование. Если появится монетизация, потребуется платный тариф или
переезд.

### Cloudflare как запасной вариант

Настройки для Cloudflare Pages оставлены в проекте: файл `public/_headers` и
команда `npm run deploy:cloudflare`. Пригодится, если `*.vercel.app` тоже
однажды закроют или если захочется зеркала для зарубежных посетителей.

### Когда появится свой домен

На Vercel: Settings → Domains → добавить домен и прописать записи у
регистратора. Сертификат выпускается сам. После этого поменять `site` в
`astro.config.mjs` и выложить заново.

Со своим доменом снова заработает и Cloudflare Pages — блокируется общий
поддомен, а не платформа. Учтите: установленное приложение привязано к домену,
поэтому при переезде с `vercel.app` его придётся переустановить.

## Ограничения

1. **Используется неофициальный API Notion** — тот же, которым пользуется сам
   сайт `notion.site`. Токен не нужен, но контракт не гарантирован и может
   поменяться без предупреждения.
2. **Синхронизация раз в час, а не мгновенно.** Мгновенно умели бы вебхуки
   Notion, но им нужен отдельный приёмник — отложено как несоразмерное.
3. **Списки несут в разметке весь каталог.** На `/music` это все 1100 релизов
   сразу, в обеих разметках. Плата за то, что страница работает без скрипта и
   целиком достаётся поисковикам.
4. **Офлайна нет.** Приложение ставится, но без сети показывает пустоту.
5. **Общего поиска нет** — поиск живёт внутри каждого списка и ищет только по
   нему.

Остальное открытое — в `docs/Что не сделано.md`.
